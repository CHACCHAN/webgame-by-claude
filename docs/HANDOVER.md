### 0.1 電車の音: VVVF Simulator の移植（Session 6、オーナーが B を選び反映済み）
- 経緯: オーナーが「電車の音にはファンが多い、雑だと好まれない」と、本物の VVVF シミュレーター（OSS）を使うよう求めた。
  ライセンスはオーナーに確認し「移植してよい」（非商用の利用規約の範囲で、設定画面のクレジットと ASSETS.md にリンクを書く）。
- **やったこと**（`frontend/src/game/audio/vvvf/`）
  - VvvfGeeks/VVVF-Simulator（C#）の計算を 1 行ずつ JS に移植: 制御パターンの解釈（`Analyze.cs`）、キャリア（ランダム変調・ビブラート・テーブル）、
    2・3 レベルの PWM（同期の特殊モード・SVM・DPWM・HO・ΔΣ）、誘導電動機の dq モデル（RK4）、車内音（トルク脈動 `DiffTe`）。
    CHM（スイッチング角テーブル）も Session 6b で移植（京急新1000 のドレミファで使用、0.3）。テーブルは使うものだけ
    `public/audio/vvvf-tables/`（8 本、365KB。パターンの JSON の `CustomPwm` に一覧、無いと `vvvf-patterns.ts` が失敗）。SHE は未使用。
  - **C# 版と 1 サンプルずつ一致を確認**: シミュレーター自身の C# ファイルをコンソールアプリにして Docker の .NET SDK で動かした
    （`frontend/tools/vvvf-ref/`、手順は README）。E231 の車内音（歯車 14:99）と 207-2000 の線間電圧が float32 で完全一致。
    単体テスト `vvvf.test.ts` が同じ比較を毎回行う（フィクスチャは C# 版の出力の間引き＋総和）。
  - YAML はそのまま読む: `frontend/tools/vvvf/*.yaml` → `npx tsx tools/vvvf-patterns.ts` → `audio/vvvf/patterns/*.json`
    （テストが古い JSON を検出）。N700 は公開パターンが無いので、同じ形式で書いた推定 `N700_ESTIMATE.yaml`。
  - ゲームへの組み込み: AudioWorklet `vvvf-sim`（`vvvf.worklet.ts`、Vite が `?worker&url` で束ねる）で約 192kHz（48kHz の 4 倍、
    スマホは 2 倍）で計算し、窓関数付き sinc で間引く → ConvolverNode でシミュレーターのインパルス応答（`public/audio/vvvf-filter.wav`）
    → 低音の共鳴を抑える EQ → 音量。速度 → インバータ周波数は歯車の歯数・車輪径・極数から（`vehicle/vvvf.ts` の `vvvfDrive`、すべり付き）。
    力行・ブレーキ・惰行（ノッチ N はシミュレーターと同じく直前のブレーキ状態を保つ）、3km/h 未満では電気ブレーキが切れる。
    モーターの回転は車輪に合わせる（惰行後の再力行で変な過渡音が出ない）。ゲートが切れて電流が消えたら計算を止める（惰行中・停車中は軽い）。
  - 重さ: V8 で 1 計算あたり約 0.5µs → 192kHz でデスクトップ 1 コアの約 9%、スマホ設定（96kHz）でその半分。
    Chrome のオフライン描画でゲームの全処理（ワークレット・畳み込み・走行音・コンプレッサー）が実時間の 21〜30%。
  - 実際のレースで確認: Chrome（GPU）で E231 のタイムアタックを自動運転し、1.4 秒でワークレットが入り、速度に応じて音量が変わること、エラーが無いこと。
- **オーナーの試聴で B に決定**（「共鳴抑えてるやつのが良かった」）: 試聴ファイル 5 本（ゲーム内の音 3 本、E231 のインバータ音だけの A/B 2 本）。
  - A = シミュレーターそのまま。インパルス応答が 150〜350Hz を約 25dB 持ち上げるため、3 パルス付近（E231 で 27〜35km/h）が他より約 20dB 大きい。
  - B = その帯域を −15dB（`TrainSound.ts` の `VVVF_BODY`）。**採用**。
  - 歯車の音は入れていない（シミュレーターの既定も無し。計算で出す歯車音は IR を通すとモーター音より 30〜50dB 大きい）。
    走行音の録音に実物の歯車音が入っている。入れるなら `TrainVvvf.gearGain`。
- 試聴ファイルの作り方: `npx tsx tools/vvvf-train-wav.ts <train> <out.wav>`（Node、インバータ音だけ。`--eq` `--os` `--gear` `--normalize`）、
  `PW_MODULE=… npx tsx tools/vvvf-game-wav.ts <train> <out.wav>`（vite preview + Chrome でゲームの音そのもの。`?export=1` のフック `__renderTrainSound`）。
- まだのこと: 銀座線1000 は東芝 207-2000 の代用のまま。（117・京成3300 は Session 6b で廃止。）

- **Blender**: 5.2.3 LTS をオーナーの PC のユーザー領域に入れた（`~/.local/bin/blender`、公式 tarball）。ヘッドレスで EEVEE・Cycles とも動く。
- **MCP 連携は未導入（オーナーの判断待ち）**: 定番のアドオン（ahujasid/blender-mcp の `addon.py` と `pip install`）の導入が、
  Claude Code の権限チェックで「外部コードの導入」として止められた。回避はしていない。入れる場合は `DISABLE_TELEMETRY=true` にし、
  アドオンのクラウド連携（Meshy・Tripo・Sketchfab・Hyper3D・PolyHaven）は使わない。それまでは Blender の Python スクリプトで作る
  （MCP も中身は Blender 内での Python 実行なので、作れる物は同じ。違いは対話的に 1 手ずつ見ながら進められること）。
- **作り方**: `frontend/tools/blender/train_kit.py`（部品の道具）＋ `tools/blender/<id>.py`（電車ごとの寸法と部品）→
  `node tools/blender-trains.cjs <id>`（Blender → GLB → gltf-transform で圧縮 → `public/models/trains/<id>.glb`）。
  `--render` で組み立ての段階ごとの絵（`/tmp/<id>-stage*.png`）。GLB をコミットするので、実行時・ビルド時に Blender は要らない。
  - 車体は断面を前後に伸ばした筒（屋根の肩の丸み）、端の面取り、運転台は前傾（rake）とふくらみ（bulge）。窓・ドア・帯・ライトは
    車体の表面に投影した板（デカール）。台車・床下機器・クーラー・パンタグラフ・スカート・連結器も部品で。
  - ゲームの電車モデルの約束（ノード car0〜car2、原点は台車中心の地面、前が +Z）は取り込みモデルと同じ。ライトは `TrainInfo.lamps`。
- **京急新1000形 1 次車**（`keikyu1000`、GLB 79KB）: 赤＋窓まわり白、黒い前面窓まわり（貫通扉は左寄り）、方向幕、上部の前照灯 2 灯、
  下部の標識灯（尾灯）。ゲーム内（Chrome・実 GPU）で夜明けと夜、ガレージと走行を確認: 前照灯・尾灯・夜の窓の明かり、3 両の並び。
  車輪径 0.86m・台車中心間 12m は推定。「1000」の表記・ワイパー・手すり・ジャンパ栓などの細部は省略。
- **ドレミファ**: シミュレーターの CHM を移植し、YAML-Files の `N1000_SIEMENS_GTO`（シーメンス GTO、歯車 14:83）をそのまま鳴らす。
  C# 版と 1 サンプルずつ一致（`vvvf.test.ts` の 3 件目）。ノッチを入れるとすべり周波数が 0.8 秒かけて立ち上がる（`SLIP_RISE`、音だけ）ので、
  0Hz から音階（ファ・ソ・ラ・シ♭・ド・レ・ミ♭・ファ・ソ）が鳴る。ゲーム内でワークレットと 8 本のテーブルの読み込みを確認。
  - ゲームの電車は起動加速度に一気に達するので、音階は約 1 秒（実車は 1.5〜2 秒）。物理にも加速の立ち上がり（ジャーク制限）を入れれば
    実車に近くなる（提案のみ。電車の加速感とメダルタイムが変わるのでオーナーの判断待ち）。

- **まれな単発のカクつき**（一部対処済み）
  - 走行途中で初めて見えた物（風車・自販機）のシェーダーをその場で作っていたのが原因の一つ。レース開始時に裏で先に作るようにした（`Game.precompile`）。
  - 残り: 1 走行に数回、1 フレームだけ 23〜32ms。原因は特定できていない（GPU のクロック変動の可能性）。
  - ゴール時に結果画面が出る瞬間に 1 回 70〜100ms。走行には影響しないので未対処。
- **路肩の岩・茂みが画面外でも描画されている**（Session 5 で試して取りやめ）
  - コース全体で種類ごとに 1 つの InstancedMesh なので、視錐台カリングが効かない。
  - 160m 四方のチャンク分け＋420m より遠いチャンクを隠す、を実装して実 GPU で交互計測したが差が出なかった
    （同じ 1.2GHz で GPU p50 7.15 → 7.19ms、描画呼び出しは 441 → 458 に増）。見積もりの 0.7〜0.9ms は「全部消した時」の差で、
    見えている分の描画がほとんどだった。変更は戻した。
- **公開サイト**
  - Cloudflare Access 等でのアクセス制限を推奨（オーナー判断）。
- **その他**
  - 朧峠のキービジュアルの車が実在車に似ている（公開前に差し替え推奨）。

### 実 GPU での性能計測と修正（Session 4）
- 計測ツール `frontend/tools/perf-gpu.cjs` を追加した。
  - 実 GPU のヘッドレス Chrome で、1 フレームごとの CPU 時間・GPU 時間（影／本描画／ポストエフェクト）・ドローコールを記録する。
  - 修正前後のビルドを交互に走らせて比べられる。
- **屈折する素材のせいで、画面全体を毎フレーム 2 回描いていた**
  - インプレッサ（`raijin`）のウインカーのレンズに屈折（transmission）が残っていた。
  - それが画面に映っている間、three.js が地形・木などすべてを屈折用にもう一度描くため、負荷がほぼ 2 倍になっていた。
  - 読み込み時に普通の半透明素材に置き換えるようにした（`CarModel.withoutTransmission`）。見た目は変わらない。
- **カーブミラーが 1m おきに並んでいた**
  - きついカーブの内側にミラーが 1m おきに立ち、オレンジ色の柵のように見えていた（朧峠で 203 本、609 ドローコール）。
  - 1 つのカーブに 1 本（一番きつい地点）にし、インスタンス描画にした（朧峠 4 本・霧降湖 2 本・天狼 4 本）。テストあり。
- 結果（1920×1080、修正前 → 修正後）
  - high: 約 110〜144fps → 約 245〜260fps。GPU 時間 5〜8ms → 約 3ms。ドローコール 最大約 2,000 → 約 500。
  - low: 103fps → 369fps（CPU 9.4ms → 2.1ms）。
  - 雨・夜明けも夜と同じ負荷。
- 注意: この GPU は自分でクロックを 800〜2,100MHz の間で変え、それだけで負荷の数字が約 2 倍変わる。
  - 比較は修正前後を交互に走らせる方法で行い、クロックも記録した。
- PROGRESS の「街灯が個別メッシュ」という記述は誤りだった（街灯はインスタンス描画済み。多かったのはカーブミラー）。
