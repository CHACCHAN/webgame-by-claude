# Fable 5.2 制作計画（2026-11-10 作成）

TOUGE NOCTURNE を「AAA 級に限界まで近づける」ための計画書。実行するのは Fable 5.2。
読む順番: **このファイル → `docs/HANDOVER.md` → `CLAUDE.md` → `docs/PROGRESS.md`**。
オーナーへの報告・質問はすべて日本語で行う。

---

## 0. オーナーの要望（2026-11-10、原文の要点）

1. 目標は BF6 や Cyberpunk 2077 などの AAA 級に、限界まで近づけた品質。
2. 高品質化で重くなる分は、アップスケーリング（例: FSR2）を入れて軽くする。
3. UI デザインを刷新する（アニメーション、クールなデザイン）。
4. ゲームシステムを見直す。例:
   - オンライン対戦は、全員が「準備完了」を押すまで開始できないようにする。
   - 車両選択が車両名だけで選びにくい。
5. オンライン対戦の待機中に、相手が選んだ車両をリアルタイムに見せる。
6. オンライン対戦の通信品質を上げる。
7. 環境にある素材（木など）を作り直す。
8. 素材は gemini web を使って「gdp」で作成・入手する。モデルは 3.8 Flash のみ。
   - 「gdp」は「Gemini web を Chrome 経由で操作する」という解釈で確定（2026-11-10 オーナー「その認識でok」）。
9. 実現できないと分かったものは、代替案と一緒に報告する。

**2026-11-10 オーナーの回答（決定事項）**
- **WebGPU に移行する**（D3 決定）。
- **Gemini は音楽・動画、必要なら画像に限る**（D2 決定。§1.4）。
- **作りかけ（エドワーズ・戦車・戦闘機）は Fable が引き継ぐ**（D1 決定。§1.2）。
- **葉の切り抜き表現を認める**（D5 決定）。
- **目標の画は BF6**（D8 決定。「限界まで近づけるだけでいい」）。
- **アップスケーラーは TRAA を採用**（D4 決定）。three.js の TRAA を土台にする。FSR の移植はしない。
- **P2P 通信を入れる**（D6 決定）。つながらなければ中継に戻る。設定で P2P を切れるようにする。
- **ダウンロードは画質設定ごとに分ける**（D7 決定）。**4K テクスチャは使わない。最大 2048×2048。**
- **オンライン対戦の上限を 5 人に増やす**（§3 Phase F5）。
- GPU はオーナーがメンテナンスで復旧を試みる（§1.1）。

## 1. 着手前に片付けること（ブロッカー）

### 1.1 GPU が消えている（オーナー作業）

**状態**
- 2026-11-10 時点で `/dev/dri` が無い。VM の GPU リセット問題（CLAUDE.md「ubuntu-dev is a Proxmox VM」）による。
- このままだと Chrome は llvmpipe（ソフト描画、1〜6 fps）でしか動かない。
- 画質・性能の作業は実 GPU（RX 5700 XT）で測れないと判断できないので、Phase A〜D はここで止まる。

**オーナーにお願いすること**
1. Proxmox から VM を「シャットダウン」する。再起動ではない。
2. 3 分以上待ってから起動する。
3. ライブのスタックは `restart: unless-stopped` なので、起動後に自動で戻る。

**Fable 側**
- 作業の最初に `ls /dev/dri` で GPU があることを確かめる。
- 無ければ Phase E〜G（UI・ゲームシステム・通信）から始める。この 3 つは GPU なしでも進められる。

### 1.4 Gemini の使い方（2026-11-10 確定）

1. Chrome に Gemini がログイン済みか。

## 2. 実現の可否と代替（先に正直に）

| 要望 | 判定 | 理由 | 代替・落としどころ |
|---|---|---|---|
| BF6・Cyberpunk と同等の画 | **完全には不可** | ブラウザ（WebGL2 / WebGPU）には次のものが無い: ハードウェアのレイトレーシング、Nanite のような仮想ジオメトリ、何十 GB のアセットのストリーミング。容量と VRAM にも上限がある。 | **「スクリーンショットと走行動画で並べても見劣りしにくい」を目標にする。** 効く順に: ①ライティングとポスト処理 ②アセットの密度と質（木・岩・路面・ガードレール） ③天候・夜の表現 ④車の材質。数値の目標は §4。 |
| FSR2 | **WebGL2 では不可**、WebGPU なら可能（作業は大） | FSR2 はコンピュートシェーダー前提で、パスが約 10 段ある。さらに次が要る: モーションベクトル、深度、reactive マスク。今のレンダラ（three.js WebGL2 ＋ pmndrs postprocessing）にはモーションベクトルが無い。 | ① WebGL2: **FSR1（EASU＋RCAS、フラグメント 2 パス）**。すぐ入る。空間アップスケールなので画質の上限は低い。 ② WebGPU: モーションベクトル（MRT）を出す。three の TRAA を土台にした**時間方向のアップスケーラー（TAAU）＋ RCAS**、必要なら FSR2 を WGSL に移植。FSR4 は機械学習で RDNA4 専用なので、Web では不可。**→ 決定: WebGPU ＋ TRAA を土台にした方式（D3・D4）。** |
| AAA 級の木・環境 | 可能（物量が大） | Blender の手続き生成と自作スクリプトの流れがすでにある。 | 近景の高密度モデル、LOD 3 段、オクタヘドラル・インポスター（Blender で焼く）、風の揺れ、GPU カリング（WebGPU）。 |
| Gemini で素材を作る | **音楽・動画・画像に限る（オーナー決定）。3D には使わない。** | 出せる曲の長さ・ループのしやすさ・動画の解像度は、試すまで分からない。 | 最初に小さく試して報告する（§1.4）。テクスチャは Blender と CC0 の写真素材が中心（Phase D.7）。 |
| 準備完了ボタン、相手車両のリアルタイム表示、車両選択の改善 | 可能 | バックエンドとフロントの通常の改修。 | — |
| 通信品質 | 可能（段階的） | 今は Reverb（WebSocket）経由の中継で、約 12 Hz の JSON。Cloudflare Tunnel を通るので UDP は使えない。 | 計測 → 時計合わせ → 送信頻度と補間の改良 → （D6 次第で）WebRTC の P2P。中継は予備として残す。 |

## 3. フェーズ計画

依存関係:
- A → B → C → D の順。D のうち木の作り直しは、A の後すぐ並行して始めてよい。
- E・F・G は A〜D と独立している。GPU が戻らない間はこちらを先に進める。
- 1 フェーズの最後ごとに次をする: オーナー確認（スクショ・動画・数値）→ コミット → 反映（デプロイ）→ PROGRESS / HANDOVER 更新。

### Phase A — 計測の土台と目標の固定（S）

**目的**: 「良くなった／重くなった」を毎回同じ条件で数値と画像で比べられるようにする。

1. **撮影ポイント**
   - 各コース 6〜8 か所の固定カメラ: スタート、ヘアピン、谷の見晴らし、林の中、直線の高速域、ゴール。
   - 時刻・天候 4 種（夜・夕・雨・明け方）。
   - 同じフレームを撮り、`docs/quality/<日付>/` に保存するスクリプトを作る。`tools/perf-gpu.cjs` の仕組みを流用する。
2. **性能の基準値**
   - `tools/perf-gpu.cjs` の course / quality / ab で、今のビルドの値を残す。
   - 2026-11-01 時点の値（PROGRESS の表）: high/night で GPU p50 約 3 ms、260 fps 程度。
   - **GPU クロックが 800〜2100 MHz で動くので、比較は必ずペアで走らせる。**
3. **予算を決める**（§4）。BF6 の参考画像（D8）を集め、目標の画作りを一枚の「ルックボード」にまとめてオーナーに見せる。

**完了条件**
- 撮影と計測がコマンド 1 つでできる。
- 今の状態の写真一式と数値が PROGRESS にある。

### Phase B — レンダラの刷新とアップスケーリング（L〜XL）

**B1. WebGPU への移行（2026-11-10 オーナー決定「WebGPUにしてください」）**

まず 1 コース・1 台・夜で、今と同じ見た目まで動かす。その上で性能をペア比較し、残りを移す。
移行の途中で解決できない問題（下の対応状況など）が見つかったら、止めて代替案と一緒に報告する。

確かめて移すもの:
- three r186 の `WebGPURenderer`（TSL / NodeMaterial）を R3F 9 で動かせるか。例: `<Canvas gl={async (p) => { const r = new WebGPURenderer(p); await r.init(); return r; }}>`。
- 移植が要るもの:
  - 自前のシェーダー 9 ファイル（`ShaderMaterial` または `onBeforeCompile`）:
    `fx/TireEffects.ts`, `fx/Exhaust.ts`, `fx/Rain.ts`, `render/Environment.ts`, `render/CarVisual.ts`, `render/JetModel.ts`, `render/TrainModel.ts`, `render/autobahnTraffic.ts`, `Game.ts`。
  - これらは TSL に書き直す必要がある。
  - pmndrs postprocessing は WebGPU で動かないので、three の `PostProcessing`（TSL ノード）に置き換える。
- 対応状況:
  - 対象ブラウザの WebGPU 対応: Chrome（Windows / Mac / Android、Linux はフラグの要否を実機で確認）、Edge、Safari 26 以降、Firefox。
  - 未対応ブラウザでは、WebGPURenderer の WebGL2 バックエンドで動くか。コンピュート前提の効果は落とす。
移行の完了条件:
- 4 コース × 4 天候で、今と同じかそれ以上の見た目。撮影ポイントの前後比較で確認する。
- 性能がペア比較で今と同等以上。
- WebGPU の無いブラウザでは、WebGL2 バックエンドで「low」品質として動く。スマホを含む。
- E2E が通る。

注意:
- Linux の Chrome では WebGPU にフラグが要るかもしれない。オーナーの Chrome と `tools/perf-gpu.cjs` の headless Chrome（`--enable-unsafe-webgpu` など）の両方で確かめる。
- 一時的に既存の WebGL の経路を残し、設定で切り替えられるようにしておくと比較しやすい。移行が終わったら消す。

**B2. アップスケーリング**（D4）

内部解像度の倍率:

| モード | 倍率 |
|---|---|
| Ultra Quality | 77 % |
| Quality | 67 % |
| Balanced | 59 % |
| Performance | 50 % |

- HUD は DOM なので、拡大の影響を受けない。
- 共通で必要なもの:
  - サブピクセルのジッター（投影行列）。
  - テクスチャの LOD バイアス（log2(内部 / 表示)）。
  - 粒子・半透明は履歴に混ぜない（reactive マスク）。
  - 次のもののモーションベクトルを正しく出す: スキニング（ゴキブリ）、毎フレーム並べ直す電車の車両、インスタンス（木の揺れ）。
- 方式（D4 決定）: three.js の TRAA を土台に、内部解像度を下げて拡大する時間方向のアップスケーラーにする。
  流れは velocity の MRT → TRAA ベースのアップスケール → RCAS 相当のシャープ化。FSR は移植しない。
  - 拡大したときの画質は自分たちで詰める。対象は細い線の保持、物陰から出た部分の扱い、残像の抑え。
  - 画質が目標に届かないときは、届かない点を画像付きでオーナーに報告する。勝手に FSR へ切り替えない。
- WebGL2 の場合: FSR1（EASU＋RCAS）。
- 設定画面に追加: アップスケーラー（オフ / TRAA アップスケール。WebGL2 の予備経路では FSR1 相当の空間拡大）、品質モード、シャープネス。

完了条件:
- 1440p の Quality モードで、ネイティブ比 1.4 倍以上の fps。
- 200 km/h で車の後ろに残像の尾が出ない。動画をコマ送りで確認する。
- 電線・フェンス・ガードレールの細い線がちらつかない。

### Phase C — ライティングとポスト処理（AAA の「画」の大半はここ）（L）

効く順に並べる。項目ごとに撮影ポイントの前後比較と、GPU コストの A/B を取る。

1. **トーンマッピングと露出**
   - ACES から AgX、または Khronos PBR Neutral へ。three は両方に対応している。
   - 物理的な露出値（EV）。
   - 時刻・天候ごとのカラーグレーディング LUT。
2. **影**
   - 太陽・月の影をカスケードシャドウ（CSM）にする。
   - ソフトシャドウ（PCSS 相当）と、近距離の接地影（コンタクトシャドウ）。
   - 今は 1 枚のシャドウマップ。
3. **環境光**
   - GTAO（three の TSL ノード）。
   - 区間ごとの事前計算の照射プローブ（SH）で、谷・林の中を暗くする。
4. **反射**
   - 雨の路面の SSR: ヘッドライト・街灯が濡れた路面に映る。夜の峠では最も効く。
   - 車の映り込みは低解像度の動的キューブマップ（数フレームに分けて更新）、または区間ごとの反射プローブ。
5. **ボリューム表現**
   - ヘッドライト・街灯の光の筋（霧・雨の中の円錐）。
   - 高さフォグ。
   - 物理ベースの空（大気散乱の LUT）。
   - 雲（低解像度のレイマーチ＋時間方向の積み上げ）。
6. **光源**
   - 街灯をすべて実ライトにする。WebGPU のタイル／クラスタ化ライティングを使う。
   - 今はプールした数個の PointLight。
7. **車の材質**
   - 塗装のフレーク。
   - レンズの内部構造と発光、レンズフレア。
   - 速度に応じたモーションブラー（物体ごと）。
   - リプレイ・フォトの被写界深度。
8. **雨**
   - 画面の水滴（車内視点）、跳ね返り、路面の水たまり（法線の変化）。

**守ること（CLAUDE.md）**
- 透過（refraction）マテリアルを場面に残さない。
- 粒子の累乗はベースを clamp する（NaN でブルームが黒くなる）。

### Phase D — 環境素材の作り直し（XL、長期）

1. **棚卸し**
   - 今あるもの: 木（`TrackScenery.treeGeometry()` の手続き生成＋遠景の板）、岩・茂み（clutter）、地面・岩・アスファルトの写真テクスチャ（ambientCG）、小物 8 種（Blender）、空。
   - 足りないもの: 下草・草、路面の補修跡・ひび・白線のかすれ、側溝、ガードレールの支柱と反射板、デリネーター、法面（吹付・落石防護網）、標識。
2. **木**
   - 地域に合う樹種を Blender のスクリプトで作る。杉・檜・ブナ／ミズナラ・赤松・竹など。コースの標高（`Landform.treeLine`）で混ぜる。
   - 近景: 2〜4 万三角形、葉は切り抜き（D5）。
   - 中景: LOD 2 段。
   - 遠景: オクタヘドラル・インポスター（Blender で 8×8 方向のアルベド・法線・深度を焼く）。
   - 頂点シェーダーで風: 幹の揺れと葉の震え。
   - インスタンス＋カリング（WebGPU ならコンピュートで GPU カリング）。
3. **草・下草**: 道路の近くだけ GPU インスタンスの草。距離で消す。
4. **岩・法面**: スカルプト＋焼いた法線マップ。法面は吹付コンクリート・網・苔。
5. **路面**: デカール（補修跡・タイヤ痕・ひび・白線の摩耗）、側溝、ガードレールの作り直し。
6. **テクスチャの形式**
   - KTX2（Basis UASTC / ETC1S）で、VRAM と読み込みを減らす。
   - `toktx`（KTX-Software）をユーザー領域に置き、glTF-Transform の `uastc` / `etc1s` を使う。
   - システムへのインストールはしない。
   - テクセル密度の基準を決める。
   - テクスチャは最大 2048×2048（D7 決定。4K は使わない）。画質設定ごとの解像度の組を作る（例: 低 512〜1024、高 1024〜2048）。
7. **テクスチャの作り方**（Gemini は音楽・動画・必要なら画像に限る: §1.4）
   - 主な手段: Blender のプロシージャルマテリアルを焼く（アルベド・法線・ラフネス・AO を同じ元から出せる）。
   - すでに使っている ambientCG（CC0、クレジット不要、このネットワークから取れる）の写真素材も使える。
     新しく取り込むときは、オーナーに一覧を見せてから。
   - Gemini の画像は「必要なとき」だけ。例: 看板の絵、オーナーが求める雰囲気の元絵。
     使うときの加工: ローカルの Python（numpy / OpenCV、ユーザー領域の venv）で継ぎ目処理・陰影除去・法線などの推定。
   - 写真から模様やロゴを切り抜かない、という今までの決まりは続ける。
8. **ルール**
   - モデルは全部自作。入れる前に、オーナーへ途中と最終のシートを見せる。
   - 予算（三角形数・テクスチャ・描画呼び出し）を守る。
   - 1 素材ごとに性能の A/B を取る。

### Phase G — 通信品質（M〜L）

**今の仕組み**
- Reverb（presence チャンネル）の client event `client-state` を約 80 ms ごとに送る。JSON。
- 受け側の補間遅延は固定の 120 ms。
- `ProxyCar` で接触する。
- 公開は Cloudflare Tunnel 経由（WebSocket のみ、UDP 不可）。

**手順**
1. **計測**
   - ゲーム内に通信の統計を出す: RTT、ゆらぎ、受信間隔、補間遅延、外挿の割合、欠落。
   - 欠落はシーケンス番号の抜けで数える。
   - クライアント側に遅延・ゆらぎ・欠落を注入する仕組みを作る。`tc netem` のようなシステム変更はしない。
   - Node のボットクライアントで、2〜3 人の対戦を再現する。
2. **時計合わせ**
   - ping / pong で、サーバー基準の時刻ずれを推定する（NTP 方式）。
   - 今の「最小遅延」の推定を置き換える。
3. **送信と補間**
   - 送信を 20〜30 Hz にする。送る内容を数値の配列に詰める。速度ベクトル・ヨーレートを含める。
   - 補間遅延をゆらぎに応じて変える（平均間隔＋2×ゆらぎ）。
   - Hermite 補間にする。
   - 位置が修正されたときは、なめらかに戻す。
   - 先に確かめること: Reverb の client event に頻度の制限があるか。
4. **WebRTC DataChannel の P2P**（D6 決定: 入れる。手順 1〜3 の後で）
   - 信頼性なし・順序なしで送る。最大 5 人のメッシュで、1 人あたり 4 本の接続（F5）。
   - 設定で P2P を切れるようにする。切ると中継だけを使う。
   - シグナリングは今の presence チャンネル。
   - つながらなければ Reverb の中継に自動で戻る。
   - 注意: 相手に IP アドレスが見える。NAT 越えには外部の STUN が要る。TURN は Tunnel 経由では置けない。
5. **堅牢さ**
   - 切断・再接続、ルーム状態の取り直し、ゴールタイムの扱い。

**完了条件**
- 次の条件で、相手の車がカクつかず、0.3 m を超えて飛ばない: RTT 100 ms、ゆらぎ 20 ms、欠落 2 %。
- 接触がどちらの画面でも同じ時に起きる。
- 数値は計測の仕組みで示す。

## 5. Fable の作業ルール（これまでの約束。破らない）

**報告**
- オーナーへの返事は日本語。
- 確認していないことを「確認済み」と書かない。検証済みと未検証を分けて PROGRESS に記録する。
- 費用を意識する。確認のラウンドは少なく、決め手のあるものだけにする。

**素材**
- 有料 API は使わない。Gemini は web の画面だけ、3.8 Flash だけ。
- モデルはすべて自作。写真は寸法と形を測るためだけに使う。
- ロゴは自作の図形で描いてよい。第三者のモデルを「自作」と表示しない。
- モデルは、オーナーが途中と最終のシートを見てから入れる。

**マシン資源**
- エージェント・Blender は同時に 3 つまで。
- Blender は `~/.local/opt/carfit/blender.sh`（スロットのロック）経由で動かす。
- Blender と Chrome を同時に動かさない。Chrome で確認する間は 3 つのロックを全部持つ。
- `free -m` の available が 2500 MB を超えていることを確かめてから重い処理を始める。
- 一時ファイルは `~/.local/opt/...` かセッションの scratchpad に置く。`/tmp` には置かない。

**ブラウザでの確認**
- `vite preview` は必ず `API_PROXY=http://127.0.0.1:9` で動かす。ライブのサーバーに書き込まないため。
- E2E は隔離したスタックで動かす。
- 他の compose プロジェクトには触らない。

**システム**
- 永続的なシステム変更はオーナーの承認を取ってから。
- `pkill -f` で自分のコマンド行に含まれるパターンを使わない。

**反映（デプロイ）**
1. 完成したものは、聞かずに `docker compose up -d --build` で反映する。
2. 新しいビルドが配信されていることを確かめる: バンドル名、GLB のハッシュ、API の 200。

**git**
- コミットメッセージの末尾に、セッションが指定する Co-Authored-By などの行を付ける。
- push と PR はオーナーに言われたときだけ。
- `docs/spec/` はコミットしない。

**GPU**
- 作業前に `ls /dev/dri` で確かめる（§1.1）。

## 6. 最初の 1 日の進め方（推奨）

1. GPU があるか確かめる（§1.1）。
2. Phase A（撮影と計測の土台）。

   GPU が無い場合: F1 → F3 → G1。
